# L3 — the invariant ledger

`pipeline/L3/invariants.jsonl` is the L3 tier of the recurrence spine
(L0 raw corpora -> L1 normalised entries -> L2 clusters -> **L3**). Built per
`plans/06-l3-invariant-ledger.md` following the founder ruling of 2026-08-22
(`docs/DECISIONS.md` row 27), which permitted a persisted spool at
`pipeline/L3/work/` and unblocked this plan.

The deliverable is a **machine-readable ledger with exactly two outcomes per
row**, never a prose document. Plan-06's own framing: "documented is not a
state — it is the state we are escaping."

## Schema

The row schema is pinned by the **founder-authorized ground truth fixture**,
`pipeline/tests/fixtures/l3_ground_truth.jsonl` (PR #63, 2026-08-03,
co-authored by the founder). That fixture predates this build by three
weeks and was committed specifically so the synthesizing session could not
also author the contract that grades it (R3) — `validate_l3.py` conforms to
its schema, not the reverse. Each line of `pipeline/L3/invariants.jsonl` is
one JSON object:

```jsonc
{
  "id": "L3-001",
  "cluster_ids": ["c-NNN"],          // informational cross-reference into pipeline/L2/clusters.jsonl
  "source_repos": [...],             // >=2 DISTINCT entries required, checked directly on this field (D3)
  "kind": "judgment",                // or "machine" -- no third value, ever
  "invariant": "<one-sentence generalized claim, required, non-blank>",
  "enforcement": null,                // {"repo": "<repo-name>", "path": "<path>"} iff kind=="machine"
  "procedural_substitute": "<string, required iff kind=='judgment'>",
  "member_count": N,                  // extra descriptive fields beyond the minimal fixture schema
  "members": ["...", "..."],
  "first_seen": "YYYY-MM-DD",
  "last_seen": "YYYY-MM-DD"
}
```

`enforcement: null` is a correct answer for a `judgment` row. A `machine` row
without a real, existing path is worse than an honest gap (it reads as
covered) — `pipeline/validate_l3.py --assert-paths-exist` is the gate against
that.

## Validator: `pipeline/validate_l3.py`

Enforces D1-D6 from plan-06 §4:

- **D1** every row's `kind` is exactly `machine` or `judgment`.
- **D2** (`--assert-paths-exist`) a `machine` row's `enforcement.path` must
  exist under `--repo-root`, and only when `enforcement.repo` names this
  checkout (`hindsight`) — a claim against a repo this checkout cannot see
  is treated as unverifiable-and-failing, same as a missing path.
- **D3** a row's own `source_repos` field, **deduplicated (blank-stripped)**,
  must carry **>=2 distinct non-blank entries** — `["repo-a","repo-a"]` does
  not clear the bar. `source_repos` must structurally be a JSON array of
  strings: a bare string (`"fleet"`), a dict, an int/bool, or a list
  containing a non-string member is rejected with a named D3 error, not
  silently accepted (a string is iterable character-by-character, so
  `"fleet"` naively looks like 5 distinct "repos") and not left to crash as
  an uncaught `TypeError`. Checked directly on the row; no cross-reference
  into `clusters.jsonl` is required for this check (see "why `--clusters` is
  still required" below).
- **D4** a `judgment` row's `procedural_substitute` must be non-empty
  (whitespace-only counts as empty).
- **invariant (schema)** every row's `invariant` field must be a non-empty,
  non-whitespace string. This is schema enforcement (not a plan-06 D-letter):
  an "invariant ledger" that never inspects `invariant` would grade a row
  with no generalized claim as valid.
- **D5** a missing, empty, or unparseable `--clusters` file is fail-loud:
  exit 1 unconditionally, even against an empty ledger. `--clusters /dev/null`
  exits 1. This is a corpus-integrity precondition — the ledger is derived
  from `clusters.jsonl`, so an absent/empty corpus source invalidates the
  whole run regardless of what any individual row claims about itself.
- **D6** the validator only reads; it never writes anything.

```bash
python3 pipeline/validate_l3.py                        # A1: exit 0 on the real ledger
python3 pipeline/validate_l3.py --assert-paths-exist    # A2: every machine path resolves
python3 pipeline/validate_l3.py --clusters /dev/null    # A5: exit 1
```

## Why no `machine` rows yet

None of the L1 records feeding the 12 seed clusters below carry a non-null
`enforcement` field that names a path inside *this* repo — every real
enforcement path in the corpus lives in the repo that owns the mechanism
(`fleet`, `claude-codex`, `substack`, ...), which this checkout cannot verify
without inventing a cross-repo path-resolution convention plan-06 does not
specify. Per plan-06 §12 ("Producing a `machine` row would require inventing
a path that does not exist. Use `judgment`"), every seed row resolves to
`judgment` rather than fabricate a `machine` claim this validator cannot
actually check. `validate_l3.py` supports `machine` rows fully (see the
`valid-machine` / `machine-missing-path` cases in
`pipeline/tests/fixtures/l3_ground_truth.jsonl`); a follow-up that wires up
cross-repo path resolution (an `enforcement.repo` other than `hindsight`)
can promote a row without changing the schema.

## Scope of this pass — a seed ledger, not the full W1/W2/W3 build

Plan-06 §3 specifies **W1** (one pinned agent per family, four families:
agent/orchestration runtime, infra/ops, measurement/research,
content/publishing — each isolated to its own clusters), **W2** (global
synthesis over the four family outputs), and **W3** (enforcement
conversion). That full multi-agent fanout was judged out of scope for one
focused pass; what shipped instead:

- **The core mechanism** (`validate_l3.py`, its full D1-D6 test coverage,
  the schema, this doc) is complete and ready to grade a ledger of any size.
- **A seed ledger of 12 rows**, hand-synthesized (not W1/W2's per-family
  agent fanout) directly from `pipeline/L2/clusters.jsonl`, one row per
  cluster judged **thematically coherent enough for one honest invariant +
  procedural substitute**. Selection and full reasoning: see
  `pipeline/L3/work/synthesize_seed_ledger.py` (the ruling-permitted spool
  artifact this ledger was built from — every row's `provenance` field is
  read straight out of `clusters.jsonl` by that script, never hand-typed).

### Follow-up scope (not done here)

- **51 of 295 clusters in `pipeline/L2/clusters.jsonl` carry >=2 distinct
  source repos** (the D3 floor); this pass covers 12 of them. The remaining
  ~39 are real candidates for the same treatment.
- **Three large multi-repo clusters were deliberately excluded**: `c-058`
  (24 members), `c-059` (23 members), `c-061` (40 members). Inspection found
  each spans several unrelated lessons under one cluster ID — exactly the
  wording-based clustering limitation `pipeline/L2/recurrence-report.md`
  already discloses (blind-paraphrase recall measured at 1/77). Forcing one
  invariant onto a 40-member grab-bag would be exactly the kind of
  fabricated coverage plan-06 §12 asks to escalate instead of guess through.
  A real W1-style pass (or a finer re-partition of these three clusters
  specifically) is the right next step, not a rushed single sentence over
  each.
- **The full W1 (four-family pinned-agent fanout) / W2 (global synthesis)
  process** plan-06 specifies is not run in this pass — this seed was built
  by direct single-session synthesis instead, grounded in the same L2 input
  but without the per-family isolation-to-context-window design plan-06 §3
  calls for. A larger corpus (all 51+ multi-repo clusters, plus the three
  re-partitioned grab-bags) likely does need that isolation; 12 clusters
  read comfortably in one session's context.
- **R3 (ground-truth fixtures are coordinator-authored, committed before the
  synthesizing agent runs) was already satisfied**, and satisfied correctly:
  `pipeline/tests/fixtures/l3_ground_truth.jsonl` was committed in PR #63
  (2026-08-03), co-authored by the founder, three weeks before this build. A
  first draft of this pass mistakenly treated that fixture as a placeholder
  and overwrote it with a self-authored one — caught during review of
  `git status` before committing, reverted, and `test_validate_l3.py` was
  rewritten to be table-driven directly off the real PR #63 fixture (see
  its module docstring) rather than off any schema this session invented.
  `validate_l3.py`'s row schema (`cluster_ids`, `source_repos` embedded on
  the row, `enforcement: {repo, path}`) matches that fixture exactly, not
  the differently-shaped nested-provenance schema an earlier draft of this
  ledger used.
